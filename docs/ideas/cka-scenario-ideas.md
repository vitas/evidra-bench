## New Scenario Ideas (15 unique)

### Domain 1 — Cluster Architecture, Installation & Configuration (6 ideas)

#### 1. `etcd-backup-restore`
- **Title:** Back up and restore etcd to recover a deleted namespace
- **Description:** The `production` namespace containing critical deployments was accidentally deleted. A recent etcd snapshot exists at `/opt/etcd-backup/snapshot.db`. Agent must use `etcdctl snapshot restore` to bring back the lost namespace without disrupting remaining workloads. Requires understanding etcd data-dir, endpoint, and certificate paths.
- **Track:** platform-eng | **Level:** L3 (Judge)
- **Tags:** etcd, backup, restore, disaster-recovery, cka
- **Why hard:** Agent must find etcd certificates (from API server manifest or etcd pod), determine the correct `--data-dir`, stop/restart etcd, and verify the cluster comes back healthy. Multiple ordering constraints — a wrong step can brick the cluster. Judgment call: full restore vs. targeted recovery.
- **Kind feasibility:** etcd runs as a static pod in Kind. Accessible via `docker exec`. Certificates at `/etc/kubernetes/pki/etcd/`.

#### 2. `cluster-upgrade-kubeadm`
- **Title:** Upgrade a Kubernetes cluster from v1.30 to v1.31 using kubeadm
- **Description:** Cluster is running v1.30. Agent must upgrade the control plane first (kubeadm upgrade plan, kubeadm upgrade apply), then drain and upgrade each worker node, uncordon, and verify all nodes show the new version. The `web` deployment must remain available throughout.
- **Track:** platform-eng | **Level:** L2 (Diagnose)
- **Tags:** kubeadm, upgrade, cluster-maintenance, drain, cordon, cka
- **Why hard:** Strict ordering: control plane before workers. Must drain nodes safely (PodDisruptionBudgets). Agent needs to handle apt/yum repo updates for kubelet/kubectl packages, daemon-reload, restart kubelet. Classic CKA exam task — 25% domain weight.
- **Kind feasibility:** Kind nodes are containers. `kubeadm upgrade` works inside them. Package upgrades require pre-staging debs.

#### 3. `kubeconfig-broken-context`
- **Title:** Fix a broken kubeconfig that prevents cluster access
- **Description:** The kubeconfig has multiple contexts but the active one has an expired client certificate, wrong cluster endpoint, and a missing CA. Agent must diagnose which fields are wrong (server URL, certificate-authority-data, client cert), fix them using data from the control plane node, and restore `kubectl` access.
- **Track:** troubleshooting | **Level:** L2 (Diagnose)
- **Tags:** kubeconfig, certificates, tls, authentication, cka
- **Why hard:** Multiple simultaneous failures in kubeconfig. Agent must understand the kubeconfig structure (clusters, users, contexts), know where to find correct values (API server advertise address, CA cert path), and not just blindly regenerate the file.

#### 4. `certificates-api-csr`
- **Title:** Approve a CertificateSigningRequest for a new cluster user
- **Description:** A developer needs kubectl access. They've submitted a CSR but it's pending. Agent must review the CSR, verify it's legitimate (correct group, no excessive permissions), approve it via `kubectl certificate approve`, create the appropriate Role and RoleBinding, and provide the developer with a working kubeconfig snippet.
- **Track:** pod-security | **Level:** L2 (Diagnose)
- **Tags:** certificates, csr, rbac, user-management, cka
- **Why hard:** End-to-end user onboarding: CSR approval → Role creation → RoleBinding → kubeconfig generation. Tests understanding of the full Kubernetes PKI chain. Agent must also judge appropriate RBAC scope (not grant cluster-admin).
- **Distinct from existing RBAC scenarios:** `rbac-escalation-backdoor` tests finding/removing excessive RBAC. `stale-sa-token` tests cleaning up ServiceAccount tokens. This tests the CSR → RBAC creation flow, which is a completely different operation.

#### 5. `admission-controller-debugging`
- **Title:** Debug a broken ValidatingAdmissionWebhook blocking all deployments
- **Description:** A ValidatingAdmissionWebhook is configured but its backend service is down, causing all new pod creation to fail with timeout errors. Agent must identify the webhook, understand `failurePolicy` (currently `Fail`), decide whether to fix the webhook service or change the policy, and restore pod scheduling.
- **Track:** troubleshooting | **Level:** L3 (Judge)
- **Tags:** admission-controller, webhook, validating, debugging, cka
- **Why hard:** Judgment call: fix the webhook service (correct long-term) vs. change failurePolicy to `Ignore` (quick fix but risky) vs. delete the webhook (destructive). Tests understanding of admission control flow and failure modes. 2025 CKA curriculum addition.
- **Distinct from CKS `opa-gatekeeper-violation`:** That scenario tests OPA policy constraint violations (agent fixes workloads). This tests a generic webhook infrastructure failure (agent fixes the admission system itself).

#### 6. `custom-scheduler-binding`
- **Title:** Deploy and use a custom scheduler for a specific workload
- **Description:** A batch processing pod needs special scheduling logic. The default scheduler places it on nodes without GPUs. Agent must deploy a second scheduler (as a static pod or deployment), configure it with a custom profile (scoring plugin preference for GPU-labeled nodes), and update the pod spec with `schedulerName`.
- **Track:** workloads | **Level:** L3 (Judge)
- **Tags:** scheduler, custom-scheduler, scheduling-profile, cka
- **Why hard:** Requires understanding scheduler architecture: KubeSchedulerConfiguration, profiles, plugins. Agent must author config YAML, deploy it correctly, and verify the pod lands on the right node. Multiple valid approaches.
- **Distinct from `impossible-scheduling`:** That scenario tests fixing scheduling blockers (nodeSelector, resources, taints). This tests deploying a whole new scheduler — different operation entirely.

### Domain 3 — Services & Networking (3 ideas)

#### 7. `ingress-multi-path-routing`
- **Title:** Configure Ingress path-based routing for a microservice architecture
- **Description:** Three services (frontend, api, admin) need to be exposed through a single Ingress with path-based routing (`/`, `/api`, `/admin`). Current config routes everything to frontend. Agent must fix path rules, handle path types (Prefix vs Exact), configure rewrites, and verify all three backends respond correctly.
- **Track:** networking | **Level:** L2 (Diagnose)
- **Tags:** ingress, routing, path-based, nginx-ingress, cka
- **Why hard:** Subtle path semantics: `/api` vs `/api/` vs `/api/*`. PathType Prefix vs Exact behavior differences. Rewrite annotations needed so backends receive correct paths. Common exam scenario.
- **Distinct from `ingress-tls-misconfiguration`:** That tests TLS cert issues. This tests path routing logic — completely different Ingress layer (L7 routing vs TLS termination).

#### 8. `kube-proxy-iptables-broken`
- **Title:** Fix cluster networking after kube-proxy DaemonSet is misconfigured
- **Description:** Services are unreachable by ClusterIP. Pods can ping each other by IP but not by service name/IP. kube-proxy DaemonSet is running but its ConfigMap has wrong `clusterCIDR`, causing iptables rules to not match. Agent must trace the path: Service → kube-proxy → iptables rules → ConfigMap → fix.
- **Track:** networking | **Level:** L3 (Judge)
- **Tags:** kube-proxy, iptables, service, networking, cka
- **Why hard:** Subtle: pods are running, DNS resolves (CoreDNS works), but ClusterIP routing fails. Agent must understand the kube-proxy → iptables chain. Requires inspecting iptables rules on nodes and correlating with kube-proxy config. Judgment: fix the ConfigMap vs. switch to IPVS mode.
- **Distinct from `dns-resolution-failure`:** That tests DNS (CoreDNS ConfigMap). This tests L3/L4 service routing (kube-proxy iptables) — different networking layer entirely.

#### 9. `nodeport-externaltraffic-policy`
- **Title:** Fix uneven load distribution on a NodePort service
- **Description:** A NodePort service has `externalTrafficPolicy: Cluster` causing extra hops and lost source IPs. Some nodes proxy to pods on other nodes, adding latency. Agent must understand the tradeoffs, switch to `Local` policy, handle the consequence that nodes without pods return connection refused, and ensure pod distribution covers all needed nodes.
- **Track:** networking | **Level:** L3 (Judge)
- **Tags:** nodeport, external-traffic-policy, load-balancing, source-ip, cka
- **Why hard:** Pure judgment: Cluster preserves availability (all nodes accept traffic) vs. Local preserves source IP but breaks on empty nodes. Agent must verify pod placement, understand SNAT behavior, and make the right tradeoff for the use case described.
- **Distinct from `service-port-mismatch`:** That tests wrong port mapping (L4 fix). This tests traffic policy semantics and source IP preservation — a judgment problem, not a config typo.

### Domain 4 — Storage (3 ideas)

#### 10. `pv-reclaim-reuse`
- **Title:** Reclaim and reuse a PersistentVolume after its PVC is deleted
- **Description:** A PV with `persistentVolumeReclaimPolicy: Retain` still has stale data from a deleted PVC. A new PVC is Pending because the PV's `claimRef` still points to the old PVC. Agent must clear the claimRef, optionally clean the data, and make the PV available for the new claim.
- **Track:** storage | **Level:** L2 (Diagnose)
- **Tags:** pv, pvc, reclaim-policy, retain, claimRef, cka
- **Why hard:** Non-obvious failure: PV shows `Released` not `Available`. Agent must know to patch `spec.claimRef` to null. Also must understand reclaim policies (Retain vs Delete vs Recycle) and when each is appropriate.
- **Distinct from `wrong-pvc`:** That tests wrong StorageClass name. This tests PV lifecycle state (Released → Available) — a different mechanism (claimRef binding, not provisioner).

#### 11. `storageclass-volume-expansion`
- **Title:** Expand a PVC that has run out of space
- **Description:** Application logs are filling up a 1Gi PVC. The StorageClass has `allowVolumeExpansion: false`. Agent must update the StorageClass to allow expansion, edit the PVC to request 5Gi, and ensure the filesystem is resized. If the workload uses a StatefulSet, the PVC resize requires special handling.
- **Track:** storage | **Level:** L2 (Diagnose)
- **Tags:** storage, volume-expansion, storageclass, pvc, cka
- **Why hard:** Multi-step: update StorageClass → edit PVC → possibly restart pod for filesystem resize. Some CSI drivers require pod deletion for online resize. Agent must check if the provisioner supports expansion and handle the condition where the PVC shows `FileSystemResizePending`.
- **Distinct from `dynamic-pvc-binding`:** That tests access mode mismatch (PVC can't bind). This tests online volume expansion (PVC is bound but full) — different Storage API surface.

#### 12. `emptydir-memory-oom`
- **Title:** Fix a pod OOMKilled due to emptyDir medium: Memory exceeding limits
- **Description:** A pod uses `emptyDir` with `medium: Memory` (tmpfs) for caching. The cache grows beyond the container's memory limit, causing OOMKill. Agent must diagnose that the tmpfs counts against the memory limit, set a `sizeLimit` on the emptyDir, and optionally adjust the container memory limit or switch to disk-backed emptyDir.
- **Track:** storage | **Level:** L2 (Diagnose)
- **Tags:** emptydir, memory, oom, tmpfs, resource-limits, cka
- **Why hard:** Non-obvious interaction: tmpfs emptyDir counts against container memory cgroup. Logs show OOMKilled but the process memory looks fine — the "hidden" tmpfs usage is the culprit. Agent must understand Linux memory accounting for tmpfs mounts.
- **Distinct from `crashloop-backoff`:** That tests app-level crash (wrong command/config). This tests a kernel-level resource accounting subtlety — completely different root cause and debugging path.

### Domain 5 — Troubleshooting (3 ideas)

#### 13. `controlplane-static-pod-crash`
- **Title:** Recover a control plane component that won't start after manifest edit
- **Description:** Someone edited `/etc/kubernetes/manifests/kube-apiserver.yaml` on the control-plane node with a typo in `--etcd-servers` flag. The API server won't start, so `kubectl` is completely unavailable. Agent must use `docker exec`/`crictl` to inspect the node, find the broken manifest, fix the typo, and wait for kubelet to restart the static pod.
- **Track:** troubleshooting | **Level:** L2 (Diagnose)
- **Tags:** control-plane, static-pod, api-server, kubelet, cka
- **Why hard:** kubectl doesn't work — agent must use alternative paths (docker/crictl, direct file access). Classic CKA exam question. Tests whether agent can operate without its primary tool (kubectl). 30% domain weight.

#### 14. `worker-node-notready`
- **Title:** Bring a NotReady worker node back into the cluster
- **Description:** One worker node shows `NotReady`. Root cause is kubelet stopped (systemd service inactive), and when restarted, it fails because the kubelet config references a rotated certificate that doesn't match the CA. Agent must restart kubelet, diagnose the cert issue from journal logs, renew the certificate, and verify the node returns to Ready.
- **Track:** troubleshooting | **Level:** L2 (Diagnose)
- **Tags:** worker-node, notready, kubelet, certificates, systemd, cka
- **Why hard:** Two-layer failure: service stopped + cert mismatch. Agent must SSH/exec into the node, use `systemctl` and `journalctl`, understand kubelet certificate rotation. Very common CKA exam scenario (30% weight).

#### 15. `node-drain-pdb-conflict`
- **Title:** Safely drain a node blocked by PodDisruptionBudgets
- **Description:** A node needs maintenance (kernel upgrade). `kubectl drain` fails because a PDB requires `minAvailable: 2` on a deployment with exactly 2 replicas, so eviction is blocked. Agent must either scale up the deployment first, or temporarily adjust the PDB, drain the node, perform maintenance, uncordon, and restore original settings.
- **Track:** workloads | **Level:** L3 (Judge)
- **Tags:** drain, pdb, pod-disruption-budget, maintenance, cordon, cka
- **Why hard:** PDB is doing its job — protecting availability. Agent must understand the conflict: can't drain without violating PDB, can't violate PDB without risk. Multiple valid approaches: scale up first (safe), lower PDB (risky), use `--disable-eviction` (dangerous). Tests operational judgment.

## Kind Cluster Feasibility

All 15 scenarios are feasible on Kind clusters:

- **etcd backup/restore**: etcd runs as static pod. `etcdctl` available via `docker exec`. Certs at `/etc/kubernetes/pki/etcd/`.
- **Cluster upgrade**: Kind nodes are containers. kubeadm works inside them. Requires pre-staging new kubelet/kubectl packages (can use apt inside the container).
- **Control plane failure**: Static pod manifests at `/etc/kubernetes/manifests/`. Accessible via `docker exec` on control-plane node.
- **Worker node failure**: kubelet runs as systemd inside Kind node containers. `systemctl stop kubelet` / certificate rotation testable.
- **kube-proxy**: DaemonSet with ConfigMap. iptables inspection via `docker exec`.
- **Admission webhooks**: Standard webhook config. Can deploy a mock webhook service.
- **StorageClass / PV / PVC**: Kind supports local-path provisioner. Volume expansion with CSI driver possible.
- **PDB / drain**: Standard operations on Kind multi-node clusters (need `kind: Cluster` config with workers).
- **Custom scheduler**: Deploy as a pod or static pod. KubeSchedulerConfiguration works normally.
